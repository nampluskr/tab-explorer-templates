# PLAN — tab_explorer_templates

> 버전: v0.1 · 작성일: 2026-09-06
>
> 이 문서는 Phase 인덱스다. 상세 설계는 여기 쓰지 않으며, task 분해는 `backlog.json`이
> 담는다. 각 Phase의 완료 조건은 `SPEC.md`의 판정 방법으로 판정한다.

**모든 Phase에 공통으로 걸리는 조건이 하나 있다** — 그 Phase를 닫을 때 **두 갈래를
각각 띄워, 더한 것이 화면에서 보이는지 사람이 확인한다**(FR-39). Phase 1이 뜨는
뼈대를 만들고 이후 Phase가 그 위에 쌓이므로, 어느 시점에도 눈으로 볼 수 없는 구간이
없다. 아래 각 Phase의 완료 조건에는 이 항목을 다시 적지 않는다.

---

## Phase 1. 뼈대와 디자인 기반

**목적** — 저장소 골격을 D-12의 배치로 세우고, 디자인 파일을 새로 쓴다. **이 단계
끝에 두 갈래가 각각 창으로 떠야 한다** — 기능은 비어 있어도 사람이 띄워 볼 수 있는
상태를 먼저 만들고, 이후 모든 Phase가 그 위에 쌓인다.

**대응 요구 ID** — FR-28 · FR-29 · FR-30 · FR-31 · FR-39

**완료 조건**

* `shared/design/` · `shell/` · `presets/` · `host_pywebview/` · `host_electron/`
  다섯이 D-12의 배치대로 있다.
* 새로 쓴 디자인 파일의 토큰 값이 v0.1 `tokens.css`와 대조해 어긋난 항목이 0건이다.
* 아이콘 자산 셋(`icons.svg` · `icons/seti/` · `icons/vscode-icons/`)이 반입돼 있고,
  세 아이콘 테마를 고를 수 있다.
* 아이콘 컨테이너 높이 다섯과 간격 토큰 넷이 모두 짝수이고, 아이콘 크기 16 · 선 굵기
  1이다.
* 저장소에 v0.1의 `structure.css`가 그대로 들어온 곳이 0건이다.
* **저장소에 빌드 단계가 0건이다**(제약 3) — 번들러 · 트랜스파일러 · 프레임워크가
  들어오지 않고, 두 갈래가 같은 껍데기 파일을 그대로 로드한다.
* **두 갈래가 각각 창으로 뜬다.** 창 안은 비어 있어도 되지만, 세 테마가 적용된 배경과
  다섯 구역의 자리는 보여야 한다.
* 갈래마다 실행 안내 문서가 있고, 저장소를 새로 받은 상태에서 그 문서의 명령만으로
  앱이 뜬다.

## Phase 2. 연결 계층과 계약

**목적** — 껍데기가 실행 환경에 요구하는 동작을 목록으로 고정하고, 두 갈래가 같은
목록을 구현하게 한다. 루트 경계와 오류 규약을 이 계층에 심는다.

**대응 요구 ID** — FR-20 · FR-36 · FR-37

**완료 조건**

* 두 갈래의 연결 계층이 구현한 동작 목록을 대조해 어긋난 항목이 0건이다.
* 목록에 없는 동작을 껍데기가 요구하는 곳이 0건이고, 껍데기 코드에 도메인 이름이
  나타나는 곳이 0건이다.
* 루트 밖 경로 셋(`..` 포함 · 절대 경로 · 루트 밖을 가리키는 심볼릭 링크)이 두 갈래
  각각에서 거부된다. **껍데기를 거치지 않고 연결 계층에 직접 넣어도 거부된다.**
* 거부 사유가 없는 대상 등 다른 오류와 구분되는 값으로 돌아온다.
* 두 갈래의 오류 구분값 목록을 대조해 어긋난 항목이 0건이다.

## Phase 3. 리소스와 탭의 핵심 모델

**목적** — 탭이 파일 경로에 묶이지 않게 하는 이번 버전의 중심을 세운다. 껍데기가
리소스 종류를 모르는 상태로 만든다.

**대응 요구 ID** — FR-1 · FR-2 · FR-3 · FR-4

**완료 조건**

* 껍데기 코드에서 종류 값과의 비교문이 0건이고, 종류 이름 문자열(`file` · `folder` ·
  `terminal` 등)이 0건이다. 프리셋과 참조 보기는 이 검색의 대상이 아니다.
* 껍데기에 없던 종류 문자열 하나를 등록하는 시험이 껍데기 코드 수정 없이 통과한다.
* 껍데기 코드가 대상 주소를 탭 식별값으로 그대로 쓰는 곳이 0건이다.
* 같은 대상을 두 번 여는 시험에서, 중복 정책이 "기존 탭"이면 탭 수 1, "항상 새 탭"이면
  2가 되고 후자의 두 탭 식별값이 서로 다르다.
* 열린 탭 전부의 대상 설명이 직렬화 왕복을 손실 없이 통과하며, 두 갈래에서 결과가
  같다.

## Phase 4. 보기의 수명과 상태

**목적** — 오래 사는 상태를 갖는 보기(터미널 세션 · NumPy 배열)를 받아낼 수 있게,
보기를 수명주기를 갖는 컴포넌트로 세운다.

**대응 요구 ID** — FR-11 · FR-12 · FR-13

**완료 조건**

* 탭을 열고 · 전환하고 · 크기를 바꾸고 · 닫는 동안 각 통보가 정의된 순서로 한 번씩
  불린다. 폐기 뒤에 그 보기가 화면을 고치려 하지 않는다.
* 탭 전환 · 패널 이동 · 껍데기 재렌더링을 각각 열 번 반복한 뒤 **보기 생성 횟수가
  1이다.** 폐기는 탭을 닫을 때만 일어난다.
* 오래 사는 상태를 가진 시험용 보기에서, 위 세 동작 뒤에도 그 값이 남아 있다.
* 보기가 맡긴 세션 상태가 탭 전환과 패널 이동 뒤에 그대로 돌아오고, 앱을 다시 켜면
  복원되지 않는다.
* 껍데기 코드가 맡은 상태의 내부를 읽거나 비교하는 곳이 0건이다.

## Phase 5. 갈아끼우는 자리 다섯

**목적** — 껍데기와 앱의 경계를 다섯 자리로 드러내, 갈아끼우는 것만으로 새 종류가
붙는 상태를 만든다. 이번 버전의 완료 조건 중 가장 중심이다.

**대응 요구 ID** — FR-5 · FR-6 · FR-7 · FR-8 · FR-9 · FR-10

**완료 조건**

* 다섯 자리 각각을 갈아끼우는 시험에서 **껍데기 코드의 변경 줄 수가 0이다.**
* 트리 항목 — 확장자 하나만 남기는 것과 폴더만 남기는 것이 각각 동작한다.
* 행 선택 매핑 — 파일 행에서만 열리는 것과 폴더 행에서만 열리는 것이 각각 동작한다.
* 보기 제공자 — 종류 둘에 서로 다른 보기가 나타나고, 등록되지 않은 종류로 탭을 열어도
  앱이 멈추지 않고 알림이 남는다.
* 중복 정책 — "기존 탭"과 "항상 새 탭"이 각각 동작하고, 가른 상태에서 판정 범위를
  조각으로 둔 것과 패널로 둔 것이 서로 다른 결과를 낸다.
* 여는 경로 — 트리를 거치지 않고 연 탭에서 중복 정책 · 고정 · 닫기 · 반대쪽 패널
  이동이 트리로 연 탭과 같게 동작하고, 그 탭을 열 때 트리 커서가 움직이지 않는다.
* **껍데기가 알지 못하는 임의의 종류 하나가 껍데기 코드 수정 0줄로 탭에서 열리고,**
  그 탭에서 미리보기 · 고정 · 닫기 · 패널 이동이 모두 동작한다.

## Phase 6. 탐색기

**목적** — v0.1이 도달한 탐색기의 작동 방식과 겉모습을 그대로 재현하되, 트리에 무엇을
표시할지는 Phase 5의 자리가 정하게 한다.

**대응 요구 ID** — FR-14 · FR-15 · FR-16 · FR-17 · FR-18 · FR-19 · FR-20 · NFR-4

**완료 조건**

* 머리글에 세 버튼만 있고 더보기 버튼이 없다. 폭 조절 손잡이가 동작하고, 탐색기를
  접었을 때 보기 영역의 폭이 0보다 크다.
* 트리 겉모습 아홉 항목(FR-16)이 모두 통과한다. 특히 깊이 3 이상에서 강조 왼쪽이
  잘리지 않고, 같은 깊이의 폴더 행과 파일 행에서 아이콘 x 좌표가 같으며, 긴 이름이
  넘쳐도 들여쓰기 폭과 아이콘 x 좌표가 짧은 이름 행과 같다.
* 지연 로딩 — 루트 선택 직후 펼치지 않은 폴더의 읽기 요청이 0건, 접었다 펼칠 때
  0건, 새로 읽기 뒤에는 다시 일어난다. 새로 읽기 뒤에도 펼침 상태가 남는다.
* 트리 키 여섯 가지가 정의대로 동작하고, 열 수 있는 행 위로 방향키를 열 번 지나가도
  탭이 하나도 생기거나 바뀌지 않는다.
* 탭을 바꿔도 트리 커서가 움직이지 않고, 접힌 폴더가 저절로 펼쳐지지 않는다. 상태
  표시줄의 경로가 활성 탭의 대상을 가리킨다.
* Phase 2의 루트 경계가 트리를 거쳐도 뚫리지 않는다.
* 루트 아래 항목이 20개로 같고 전체 수만 다른 fixture 둘에서, **큰 쪽 중앙값이 작은
  쪽의 2배를 넘지 않는다.**

## Phase 7. 껍데기의 화면과 사용성

**목적** — 창 · 메뉴 · 상태 표시줄 · 탭 · 가르기 · 조합키 · 설정을 v0.1과 같게
만들어, 기존 사용성이 회귀하지 않게 한다.

**대응 요구 ID** — FR-21 · FR-22 · FR-23 · FR-24 · FR-25 · FR-26 · FR-27

**완료 조건**

* 다섯 구역이 겹치지 않고, 최대화 토글과 창 밖 최대화 상태 반영이 동작한다.
* 세 메뉴가 열리고 바깥을 누르면 닫힌다. 팝오버가 자신이 속한 버튼의 왼쪽 끝에 맞춰
  열리며, 메뉴마다 서로 다른 자리에서 열린다.
* 상태 표시줄 오른쪽에 이름 · 버전 · 빌드일자 · 갈래 이름 네 값이 있고, 세로 띠의
  토글로 접히고 펴진다.
* 미리보기와 고정이 v0.1과 같게 동작하며, **트리를 거치지 않고 연 탭(FR-9)에서도
  같다.**
* 가른 상태에서 초점 조각이 표시되고, 탭을 반대쪽으로 옮겨도 보기 인스턴스가
  유지된다. 조각의 탭을 모두 닫으면 가르기가 풀리고, 셋 이상으로 갈리지 않는다.
* 껍데기가 예약한 조합키가 열한 개이고, 그 밖의 조합키에 반응하지 않고 보기에 그대로
  전달한다.
* 다시 켠 뒤 화면 상태(테마 · 아이콘 테마 · 탐색기 폭 · 상태 표시줄 표시)는 유지되고
  **열린 탭은 0개다.** 망가진 설정 파일로도 기본값으로 뜬다.
* 루트 경로를 인자로 넘겨 실행하면 그 루트로 뜨고, 없는 경로나 파일 경로를 넘기면
  기본 동작으로 떨어진다.

## Phase 8. 프리셋과 참조 보기

**목적** — 복사한 직후 동작하는 상태를 만들고, 갈아끼우는 방법이 코드로 드러나게
한다.

**대응 요구 ID** — FR-32 · FR-33

**완료 조건**

* 파일 프리셋과 폴더 프리셋이 각각 트리 표시 · 행 선택 매핑 · 중복 정책 셋을 채우고
  있고, 그 결과가 FR-32의 표와 같다.
* 프리셋을 바꿀 때 껍데기 코드의 변경 줄 수가 0이다.
* 두 프리셋이 갈아끼우는 자리 밖의 껍데기 코드를 각자 갖고 있지 않다.
* 파일 프리셋의 참조 보기가 파일 이름만 출력하고 **내용을 읽는 요청을 한 번도 하지
  않는다.** 폴더 프리셋의 참조 보기가 폴더 주소만 표시한다.
* 참조 보기를 다른 것으로 바꿀 때 껍데기 코드의 변경 줄 수가 0이다.

## Phase 9. 두 갈래 동등성과 마감

**목적** — 두 갈래가 같은 결과를 내는지, 실물 앱의 요구를 실제로 받아내는지, v0.1의
검사가 전건 통과하는지를 확인하고 버전을 닫는다.

**대응 요구 ID** — FR-34 · FR-35 · FR-38 · FR-39 · NFR-1 · NFR-2 · NFR-3 · NFR-5 ·
NFR-6

**완료 조건**

* `markdown_browser`의 요구 셋(확장자 필터 · 트리를 거치지 않고 새 탭 · 경로를 인자로
  받아 시작)을 모두 끼운 시험용 앱이 동작하고, **그 앱을 만드는 동안 껍데기 코드의
  변경 줄 수가 0이다.**
* 두 갈래가 각각 실행되고, 같은 껍데기 파일과 디자인 파일을 가리킨다.
* **`host_pywebview/`를 지운 뒤 Electron 갈래가, `host_electron/`을 지운 뒤 pywebview
  갈래가 각각 실행된다.** `shell/`과 `presets/` 아래에 특정 호스트에만 있는 파일이
  0건이다.
* NFR-1의 측정표를 v0.1과 대조해 어긋난 값이 0건이고, 사람이 두 화면을 나란히 보아
  요소 누락 · 잘림 · 겹침이 없다.
* 같은 측정표를 두 갈래끼리 대조해 어긋난 값이 0건이다.
* 세 테마 모두에서 본문 대비 4.5:1 이상, 큰 글자와 주요 구분선 3:1 이상이다.
* 열두 가지 기능 각각에 눌러서 도달하는 경로가 있다.
* 껍데기의 공개 동작 중 시험이 없는 것이 0건이고, **v0.1의 32건에 대응하는 13개
  묶음이 전건 통과하며 건수 합이 32다.**
* 갈래별 실행 안내 문서의 조합키 표가 FR-25의 열한 가지와 어긋난 항목이 0건이다.
* `DOC-SCHEMA.md` 9절의 초기화 검사 목록과 `backlog validate`가 전건 통과한다.

## Phase 사이의 의존

| Phase | 선행 | 이유 |
| --- | --- | --- |
| P1 | 없음 | 바닥. 스택 판정이 여기서 갈리면 뒤가 전부 흔들린다 |
| P2 | P1 | 배치가 정해져야 연결 계층의 자리가 생긴다 |
| P3 | P1 | 껍데기 골격 위에서 모델을 세운다 |
| P4 | P3 | 탭 모델이 있어야 보기의 수명을 걸 수 있다 |
| P5 | P3 · P4 | 탭 모델과 보기 수명이 정해지지 않으면 자리의 계약을 쓸 수 없다 |
| P6 | P2 · P5 | 트리 항목 자리와 루트 경계를 모두 쓴다 |
| P7 | P4 · P5 | 미리보기·가르기가 보기 수명과 여는 경로를 쓴다 |
| P8 | P5 · P6 · P7 | 프리셋이 세 자리를 채우려면 셋이 모두 서 있어야 한다 |
| P9 | 전부 | 마감 |

P6과 P7은 서로 독립이라 순서를 바꿔도 된다.
