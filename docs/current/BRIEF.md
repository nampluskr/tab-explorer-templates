# BRIEF — tab_explorer_templates

> 버전: v0.1 · 작성일: 2026-09-06
>
> 이 문서는 첫 버전에서 무엇을 왜 원하는지만 담는다.

---

## 1. 배경

`explorer_templates` v0.1은 파일 탐색기 형태의 껍데기를 만든 MVP다. 루트 폴더를
열고, 트리에서 파일을 골라 탭으로 열며, 좌우로 가른 패널 사이에서 탭을 옮기는 UI를
pywebview와 Electron 두 갈래로 제공했다.
계획 외 개선 68건을 거치며 색·글꼴·아이콘·간격의 시각 체계가 정착했고, 자동 테스트
32건이 그 상태를 지키고 있다.

그런데 그 껍데기는 파일을 전제로 굳어 있다. 탭을 열고 닫고 옮기는 함수의 키가 모두
파일 경로 문자열이고, 껍데기 전체가 한 파일 850줄에 들어 있어 앱이 갈아끼울 수 있는
자리는 23줄뿐이다.

같은 껍데기를 이미 한 번 더 짰다는 사실도 있다. `markdown_browser`는 트리와 탭을
갖춘 같은 형태를 독립적으로 967줄로 구현했다. 두 벌이 이미 존재하고, 앞으로 만들
앱은 넷이다.

### 이 결론에 이른 경위 — 기획 둘을 쓰다가 얻은 것

이 프로젝트는 처음부터 구상된 것이 아니다. 파일 쪽과 폴더 쪽을 각각 기획하다가
**둘 위에 일반화된 상위 구조가 먼저 있어야 한다**는 결론에 이르러 나왔다. 그 두
기획이 재료다.

**`file_tab_explorer_templates` v0.2 (2026-09-05).** `explorer_templates`를 잇는
v0.2로 잡고, 탭이 파일 경로에만 종속되지 않게 일반화하려 했다. 이때 이미 아쉬운
점을 넷으로 적어 뒀다 — 탭의 정체성이 파일 경로와 결합돼 파일 아닌 대상을 표현하기
어렵다, 보기의 수명과 탭의 수명이 나뉘어 있지 않아 상태를 계속 들고 있어야 하는
보기를 붙이기 어렵다, 껍데기와 플러그인의 경계가 파일 보기에는 맞지만 폴더나 장기
실행 세션으로 넓어지는 상황은 검증되지 않았다, `explorer_templates`라는 이름이 그
역할을 드러내지 못한다. 여기서 탭을 종류·식별값·대상 설명·보기 상태로 가르는 안이
나왔고, 목적을 "리소스 탭 기반 확립"으로 좁혀 실제 응용 기능은 넣지 않기로 했다.

**`folder_tab_explorer_templates` v0.1 (2026-09-05).** 위 v0.2가 완성되면 그 위에
올릴 첫 파생으로 기획했다. 폴더를 부가 정보가 아니라 **탭의 주 대상**으로 삼아,
파일이 아닌 리소스가 같은 열기·전환·이동·닫기 규칙을 타는지 검증하는 것이 목적이었다.

두 기획을 나란히 놓고 보니 층이 하나 더 있었다. 앞의 것은 이름과 달리 파일 전용이
아니라 **일반화 그 자체**였고, 뒤의 것은 그 일반화의 검증 사례였다. 파일 계열과
폴더 계열을 각각 템플릿으로 두면 공통부가 갈라지고(D-2), 계열 레이어를 두면 전파
비용만 늘어난다(D-7). 그래서 두 기획을 하나로 합쳐, 종류를 모르는 껍데기 한 벌과
그 위의 프리셋이라는 구조로 다시 세운 것이 이 프로젝트다.

### 폴더 계열을 왜 만드는가

파일 탭 탐색기에서 트리의 폴더는 파일을 찾기 위해 펼치고 접는 항목일 뿐이고, 실제
탭이 되는 것은 파일이다. 그런데 다음 두 가지를 하려면 폴더 자체가 독립된 탭으로
열리고 유지돼야 한다.

- **여러 폴더를 작업 단위로 나란히 비교하는 것**
- **각 폴더를 작업 위치로 삼아 폴더마다 별도의 도구를 돌리는 것**

여기서 나오는 앱이 둘이다.

| 앱 | 폴더 탭을 무엇으로 쓰는가 | 그래서 필요한 것 |
| --- | --- | --- |
| 멀티터미널 | 고른 폴더를 작업 위치로 삼아 탭마다 터미널 세션을 띄운다 | 같은 폴더에서 여러 세션을 열 수 있어야 하므로, 대상 주소를 탭 식별값으로 쓸 수 없다. 장기 실행 프로세스를 안고 있어야 하므로 탭 수명 동안 보기가 살아 있어야 한다 |
| 폴더 간 파일 관리 툴 | 좌우 패널에서 서로 다른 폴더를 열고 그 사이에서 파일을 옮긴다 | 좌우 패널이 서로 다른 폴더 탭을 갖고, 중복 판정이 패널 단위로 이뤄져야 한다 |

이 둘은 위험과 검증 기준이 서로 다르다. 터미널은 장기 실행 프로세스와 실시간
입출력을 다루고, 파일 관리자는 되돌릴 수 없는 작업과 두 패널 사이의 규칙을 다룬다.
그래서 하나의 템플릿에 함께 넣지 않고 각각 별도의 앱으로 만든다. 이번 버전이 만드는
것은 그 둘이 꽂힐 자리다.

폴더 계열의 요구가 이번 버전의 설계를 실제로 움직인 곳이 셋 있다. 대상 주소와 탭
식별값을 가른 것, 보기를 무상태 함수가 아니라 수명주기를 갖는 컴포넌트로 둔 것,
중복 판정의 범위를 갈아끼우는 자리로 뺀 것이다. 셋 모두 파일만 보고 있었으면 나오지
않았을 요구다.

| 계열 | 만들 앱 |
| --- | --- |
| 파일 | 마크다운 뷰어 · FFT analyzer |
| 폴더 | 폴더 간 파일 관리 툴 · 멀티터미널 |

마크다운 뷰어는 `markdown_browser`를, FFT analyzer는 `fft-analyzer-pywebview`를 이
껍데기 위에서 다시 만드는 것이다. 후자는 지금 트리도 탭도 없는 분석 도구지만,
이미지 파일을 트리에서 골라 탭마다 ROI 분석을 띄우는 형태로 바꿔 재작성한다.

이 프로젝트는 `explorer_templates`를 잇지 않고 새로 시작한다. **재작업 대상 셋은
2026-09-06에 모두 `_archive`로 동결했다.** 구조와 코드는 참고 자료로만 본다.

| 참고할 것 | 동결 위치 |
| --- | --- |
| 파일 탐색기 껍데기 · 결정 25개 · 디자인 토큰 | `_archive\260904_explorer_templates\` |
| 마크다운 뷰어 | `_archive\260813_markdown_browser\` |
| FFT analyzer | `_archive\260826_fft-analyzer-pywebview\` |

세 폴더 모두 `node_modules`·`dist` 같은 재생성 가능한 산출물은 이관하지 않았다.
실행해 봐야 하면 `npm ci` 또는 빌드 스크립트로 다시 만든다.

위 경위의 기획 둘도 이 프로젝트가 대체하므로 2026-09-06에 함께 동결했다. 요구는
이미 뽑아내 이 문서와 `DECISIONS.md`·`SPEC.md`에 옮겼고, 근거와 배제한 대안을 다시
볼 일이 있을 때만 아래를 연다.

## 2. 이번 버전에서 풀고 싶은 문제

네 앱이 공유하는 것은 껍데기 거의 전부다. 창, 메뉴 줄, 탐색기 트리, 좌우 패널,
탭 줄, 상태 표시줄, 설정 저장, 두 갈래의 호스트 연결까지 같다. 서로 다른 것은
**트리가 무엇을 보여주는가**, **행을 고르면 무엇이 열리는가**, **탭 안에 무엇이
그려지는가** — 이 세 축뿐이다.

지금은 그 세 축이 껍데기 코드 안에 녹아 있어서, 새 앱을 만들 때마다 껍데기를 통째로
복사한 뒤 안쪽을 뜯어고치게 된다. 그러면 아이콘 하나를 고칠 때 여섯 벌을 고쳐야
한다.

v0.1에서는 껍데기를 리소스 종류와 무관하게 만들고, 달라지는 축을 **밖에서 갈아끼우는
자리**로 드러내고 싶다. 갈아끼우는 자리는 다섯을 예상한다.

- 트리에 무엇을 표시할지 고르는 자리
- 행을 골랐을 때 어떤 종류의 탭을 열지 정하는 자리
- 탭 안을 그리는 자리
- 같은 대상을 다시 열 때 기존 탭을 쓸지 정하는 자리
- 트리를 거치지 않고 탭을 여는 자리

이 다섯을 갈아끼우는 것만으로 네 앱의 껍데기가 나오는 상태를 원한다. 껍데기 자체는
한 벌만 유지한다.

## 3. 하지 않을 것

- **네 앱 중 어느 것도 만들지 않는다.** 마크다운 렌더링, FFT 분석, 파일 복사·이동·
  삭제·이름 변경, 터미널 프로세스 실행은 이번 버전에 들어가지 않는다.
- 폴더 탐색기와 멀티터미널의 실제 기능을 구현하지 않는다. 이번에 만드는 것은
  그것들이 꽂힐 자리다.
- **시각 체계를 다시 정하지 않는다.** 디자인 파일은 새로 쓰되, 거기 적는 색·굵기·
  글꼴·너비·높이·아이콘은 `explorer_templates` v0.1의 값을 참고한다. 이번 버전은
  구조를 고치는 버전이지 겉보기를 고치는 버전이 아니다.
- **탐색기의 작동 방식을 다시 설계하지 않는다.** 트리의 키 조작, 지연 로딩과 기억,
  커서와 활성 탭의 분리는 v0.1이 도달한 것을 그대로 재현한다.
- 설치형 라이브러리나 패키지로 만들지 않는다. 복사해서 쓰는 템플릿으로 둔다.
- 코드 생성기나 설치 마법사를 만들지 않는다.
- 요약 지표·목록 표 위주의 UI(Dashboard 형태)를 다루지 않는다.
- 모바일과 클라우드 배포를 고려하지 않는다.
- pywebview와 Electron 중 하나를 버리거나 하나로 합치지 않는다.
- 설치 프로그램 제작과 clean 환경 배포 검증을 하지 않는다.

## 4. 완료 조건

> **껍데기가 종류를 모른다** — 껍데기 코드에서 리소스 종류를 직접 비교하는 분기가
> 0건이다. 종류를 아는 코드는 갈아끼우는 자리 안에만 있다.
>
> **갈아끼우는 것만으로 새 종류가 붙는다** — 시험이 등록한 임의의 종류 하나가
> 껍데기 코드 수정 0줄로 탭에서 열린다.
>
> **탭 수명 동안 보기가 살아 있다** — 그 탭을 다른 탭으로 전환했다가 돌아오거나
> 반대쪽 패널로 옮겨도 보기 인스턴스가 다시 만들어지지 않는다. 탭을 닫을 때만
> 폐기된다.
>
> **실물 앱의 요구를 받아낸다** — `markdown_browser`가 이미 갖춘 세 가지(확장자로
> 트리 항목 거르기, 트리를 거치지 않고 새 탭 열기, 파일 경로를 인자로 받아 시작)를
> 껍데기 코드 수정 0줄로 충족한다.
>
> **기존 사용성이 회귀하지 않는다** — 미리보기 탭, 고정 탭, 같은 대상 다시 열기,
> 탭 닫기, 좌우 패널 이동이 `explorer_templates` v0.1과 같게 동작한다. v0.1의
> 자동 테스트 32건에 대응하는 검사가 전건 통과한다.
>
> **겉보기가 v0.1과 같다** — 세 테마(`white`·`gray`·`dark`, 기본 `gray`)와 세 아이콘
> 테마(Simple·VS Code Built-in·VS Code Icons)가 그대로 있고, 새로 쓴 디자인 파일의
> 값이 v0.1의 `tokens.css`와 일치하며, 아이콘을 담는 컨테이너 높이가 전부 짝수다.
>
> **탐색기가 v0.1과 같게 움직인다** — 트리 키 여섯 가지(`↑` `↓` `→` `←` `Enter`
> `Home`/`End`), 한 단계씩 읽는 지연 로딩과 읽은 폴더 기억, 새로 읽기 후 펼침 상태
> 유지, 트리 커서와 활성 탭의 분리, 루트 경계 밖 거부가 모두 v0.1과 같다.
>
> **두 갈래가 같다** — 위 항목들이 pywebview와 Electron에서 같은 결과로 확인된다.
